# Astraea flight/recovery output dictionary

**Dictionary revision:** `RMP10-C06/2`

**Scope:** the committed legacy 6-DOF flight and recovery readouts, their plots, the Build export trace, and the read-only historical Saved Runs presentation.
**Source base at authoring:** `d278d49421cdd6ecd3e390c8ce3fdd4524e4f692`, plus this increment's explicitly listed changes.

This is a definition and consumer map, not physical validation. It does not add a TypeScript runtime evaluator, change a model/default/threshold/schema, promote sampled peaks to continuous maxima, or claim competition compliance. The production values originate in Rust and cross the bridge as `SixDofSimulationResult`; `src/sim/sixDofSimulator.ts` is cited only for the read-only DTO/oracle declarations.

## 1. Canonical data, frame, clock, and trace contract

The common source chain is:

1. `crates/astraea-core/src/six_dof.rs::SimulationResult` and `SimEvent` contain native results.
2. `crates/astraea-engine/src/models.rs::to_flight_dto` copies them to `FlightResultDto` without display rounding.
3. `src/console/data/adapter.ts::toFlightRun` constructs `FlightRun.summary`, `events`, `series`, `sampledMaxQ`, and `gates`.
4. `src/console/data/recoveryResults.ts::flightOutputDictionary` projects those same retained results into `Build`'s `simulation.outputs`; it does not recompute a physical quantity.

Common conventions:

- **Timebase:** seconds from ignition, with the native ignition event at `t = 0` (`six_dof.rs`, initialization of `t` and the `Ignition & Rail Guidance` event). Event/root clocks and result clocks are not derived from rounded plot timestamps.
- **Frame/datum:** ENU `x` East, `y` North, `z` Up; altitude is m AGL above the flat `z = 0` touchdown plane (`models.rs::to_flight_dto`, manifest `frames` and `ground`). Position drift uses only East/North. Airspeed is air-relative; ground speed is the norm of navigation-frame velocity.
- **Canonical units:** the `Result.unit` values below are SI (with `g`, `deg`, and dimensionless Mach explicitly identified). UI conversion in `src/console/kit/units.ts::show` changes presentation only.
- **Qualification:** `Result.confidence` and factual `Result.reason` are assigned by `adapter.ts::toFlightRun`, `aeroLevel`, `flightLevel`, `aeroConfidence`, `INERTIAL`, `RECOVERY`, and `DRIFT_REASON`. `unknown` is a qualification level, not by itself an unavailable value. No level here means measured flight accuracy or competition approval.
- **Availability/null:** Build emits `{ value, unit, confidence, reason?, available, unavailableReason? }`. An available finite value retains its canonical binary64 number. An unavailable or non-finite value has `value: null`, `available: false`, and a factual reason; confidence is preserved rather than silently promoted. An optional quantity with no source samples (notably `maxQ`) is absent, not zero-filled. With no committed run, `simulation` is null.
- **Trace identity:** Build writes `simulation.outputDictionary = { revision: "RMP10-C06/2", document: "docs/internal/output-dictionary.md", units: "canonical SI; null when unavailable; no display rounding" }`, plus `simulation.outputs`, raw `events`, `sampledMaxQ`, run/engine identity, validity, envelope, native `offNominalExcursion`, termination, and landing-nominal status.
- **Saved archive identity (project schema 1.11.0):** `src/application/runCases.ts::withRunCases` writes `case.flightOutputs = { dictionaryRevision, outputs, flags, sampledMaxQ? }` for new flight cases. `outputs` is the same `flightOutputDictionary` projection (no second formula); `flags` preserves `validity`, `enveloped`, `offNominalExcursion`, `landingNominal` and optional `terminationReason`; `sampledMaxQ` preserves the retained peak context. `src/application/savedFlightOutputs.ts::parseSavedFlightOutputs` is strict: exact keys, known output ids, finite-or-null availability invariants, qualification enums and peak-counter bounds. Each id must carry its producer's canonical SI unit from the shared `SAVED_FLIGHT_OUTPUT_UNITS` table (`m`, `s`, `m/s`, `1`, `g`, `Pa`, `J`, `deg`), so an archive cannot silently reinterpret a metric value. `flightOutputs.outputs.{landingSpeed,landingEnergy,apogeeToTouchdown}` must be unavailable when the archived flags say timeout or no nominal touchdown, using the same `src/application/flightLanding.ts::landingAvailability` rule as the readouts. Documents before 1.11.0 have no `flightOutputs` and are never backfilled; injecting it into an older schema fails closed.
- **Display precision is not accuracy:** Build outputs and gate values are not display-rounded. UI defaults from `units.ts::show` are: distance 0 decimals (m or ft), speed 1 decimal in m/s or 0 in ft/s, energy 0 decimals, time 1 decimal s, angle 1 decimal degree, Mach 2 decimals, acceleration 1 decimal g, and pressure 1 decimal kPa in metric. Event-table time uses `toFixed(2)` s. These choices imply neither input nor measurement precision.

## 4. Events, plots, and intervals

### Recorded event fields

`FlightEvent` is adapted from native `FlightEventDto` by `adapter.ts::toFlightRun`: `t = e.time`, `altitude = e.altitude`, `velocity = e.velocity`, with canonical labels from `src/application/flightEvents.ts::EVENT_LABEL`. Native events are sorted by the adapter. The strict saved parser requires canonical labels, finite nonnegative non-decreasing times, exact keys, and `derived: true` only for Sampled Max-Q; it does not interpolate, repair, reorder, or reconstruct.

- **Native event time:** seconds from ignition at the native served/refined event. Event altitude is m AGL. Native event velocity is `serve_root.v.norm()` for rail exit/burnout/apogee-drogue and `e_ground.v.norm()` for touchdown; Main is `serve_root.v.z.abs()` (vertical speed magnitude). These are not interchangeable definitions.
- **Apogee · drogue:** this is recovery activation at `ev_time`, which can be delayed. Physical peak altitude/time remain `apogee`/`apogeeTime`; the activation marker must not start the Apogee → touchdown interval.
- **Sampled Max-Q:** the only derived event, inserted from the same bounded display-sample peak as `summary.maxQ`; its event speed is that sample's airspeed and its altitude is the rounded display altitude. It is not a native continuous event root.
- **UI/export resolution:** Flight/Recovery event tables display time with 2 decimals and distance/speed through `ValueUnit`; Saved Runs prints exact stored scalar strings in stored units; Build exports raw event numbers. No consumer recalculates event time, altitude, or speed.

### Plots and time series

`adapter.ts::toFlightRun` builds `series.t` and every channel from the same `telemetry` array used for sampled Max-Q and FlightPose. `FlightTimeline.tsx::FlightTimeline` uses that array directly for altitude, airspeed, Mach, AoA, and q; it does not resample summary values or compute new peaks. Nonterminal native display samples are decimated/rounded (time 0.001 s, altitude/position/speed/acceleration 0.1, Mach 0.001, AoA 0.01 deg, q 1 Pa); the terminal point is full precision as documented in `six_dof.rs`. Plot scrubbing selects the nearest retained sample, never an interpolated physical state.

The telemetry `pitchDeg`/`rollDeg`/`yawDeg` fields are a non-authoritative
presentation of the sample's canonical `q` under `attitude-euler/1.0.0`:
`R_NB = Rz(yaw)·Rx(pitch)·Ry(roll)`, with `pitchDeg = asin(2(wx+yz))` the nose
elevation, `rollDeg = atan2(2(wy−zx), 1−2(x²+y²))` the right-handed spin about
the longitudinal +Y, and `yawDeg = atan2(2(wz−xy), 1−2(x²+z²))` the right-handed
rotation about +Z (a launch azimuth `a` reads `yawDeg = −a`). At
`|pitch| = 90` the roll/yaw split is a gauge: roll is pinned to 0, pitch to
±90, and yaw carries the combined z-rotation, so the triple still reconstructs
the attitude; the values remain non-authoritative and `q` is canonical. No
current chart reads the triple. Telemetry written before the corrected
extraction — the run's recorded `engineIdentity` is the boundary — carries the
previous defective formulas and is not a physical attitude (in the retained
vertical fixtures the old pitch stayed at 90° while the vehicle pitched over).
Those archives keep their recorded bytes and are never recomputed; their
`pitchDeg`/`rollDeg` must not be compared with post-correction values.

The only derived event interval in the current readout/trace is **Apogee → touchdown**, defined above. Other event-to-event durations are not fabricated. If a future consumer needs one, it must name two recorded non-derived events and subtract their clocks with explicit duplicate/missing-event and qualification semantics; a deployment marker is not the physical apogee.

### Project archive resource policy

`src/io/files.ts` separates two explicit software budgets, not physical
tolerances:

- **Native project archives — 64 MiB.** Save project file, Build's project
  export and Open/drop of `.astraea.json`/`.astraea`/`.json` all measure the
  same serialized UTF-8 byte length (`projectArchiveBudget`) and refuse above
  `MAX_PROJECT_ARCHIVE_BYTES` before any write or read. The limit is sized from
  the observed archive: two full-telemetry runs serialize to about 9.6 MB, and a
  full 5000-sample run to about 4.8 MB, so 64 MiB holds roughly thirteen such
  retained runs. Above it the app refuses rather than creating a file it cannot
  reopen. Project files retain every saved run and its telemetry; the refusal
  states that, keeps the current design open, and never promises that the
  browser slot (a separate, quota-bound local option, not a backup) will accept
  the project.
- **Foreign imports — 8 MiB.** `.ork`, `.rkt`, `.eng` and `.rse` keep the
  smaller pre-parse protection (`MAX_FOREIGN_IMPORT_BYTES`).

The budget is checked on actual `File.size` before reading and on the serialized
text before any save dialog, picker, download or ZIP write. It does not
compress, truncate, drop samples or change the schema; serialization (including
signed zero) and stale-write semantics are unchanged.

## 5. Saved Runs and export distinctions

- `src/application/runCases.ts::flightSummary` still archives finite scalar values or null for compatibility, and now also records `offNominalExcursion` for new flights. It does not rerun or recompute.
- New flight cases also archive `flightOutputs`, the canonical dictionary above. In Saved Runs, a comparison where **both** selected records are flights with `flightOutputs` renders canonical keys from that dictionary: values and units through `units.ts::show`, qualification through `ResultValue`, deltas through the existing `DeltaChip` (same unit conversion and small-difference suppression as the live Flight table). Unavailable entries show `N/A — reason` on both sides and withhold the delta; an available `0` remains `0`. Landing/descent rows also re-apply the record's archived landing flags at the UI boundary, so an in-memory archive that advertises an available landing under timeout/non-nominal flags still shows `N/A — reason`. A delta is withheld (`—`) if the two stored units disagree or either is not the canonical unit for that id; recorded values are shown as stored, never converted or rewritten. Mixed flight/ensemble kinds never produce numerical deltas.
- If either record lacks `flightOutputs` (pre-1.11 summary-only or ensemble), Saved Runs keeps the legacy stored-unit table and labels the comparison historical and unqualified; it does not substitute current defaults, current units, or current qualifications. `SavedRuns.tsx::savedLanding` still applies the shared landing availability rule to those legacy cells.
- Each saved flight with `flightOutputs` also exposes its dictionary revision, validity/envelope/off-nominal/landing/termination flags and sampled max-Q context read-only, including the retained-empty telemetry disclosure that already exists for `telemetry: []`.
- The project archive may retain raw finite landing scalars even when the readout correctly labels them unavailable; retention is not a landing claim. Build's output dictionary makes availability explicit and emits null for those landing outputs.
- Build KML consumes the same run's native telemetry positions, not a second trajectory. It requires a current valid run, telemetry, explicit `terminationReason === "touchdown"`, and shared nominal availability. `hasKmlNominalTouchdown` is the single check used by preview refusal and final export.

## 6. Duplicate-formula audit and findings

### Confirmed / resolved

1. **Recorded descent interval (prior RMP10b defect remains fixed).** `Recovery.tsx::RecoveryStage` calls only `recordedDescentInterval`; Build calls the same helper through `flightOutputDictionary`. Tests use apogee 10 s, delayed drogue 13 s, touchdown/flight end 30 s and require 20 s, never 17 s. Missing/duplicate/derived touchdown and invalid/inconsistent clocks remain unavailable. No delayed-marker formula was found in Build, Saved Runs, RecoveryCard, or plots.
2. **Landing deltas (prior RMP10b/RMP15a behavior remains fixed).** `Flight.tsx::ResultsTable` checks both `landingAvailability(run)` and `landingAvailability(prev)` before either landing delta. `SavedRuns.tsx` applies the equivalent shared helper to both saved records (and, for canonical records, the archived availability already produced by that helper). Existing and new tests cover current/previous non-nominal records, timeout despite a contradictory nominal flag, and a both-nominal control.
3. **Missing Build recovery/output projection — resolved here.** Before this increment `Build.tsx::useExportCheck` had no `simulation.outputs`; the trace could not demonstrate readout/export equality. It now exports every available canonical `RunSummary` numeric result plus the shared recorded descent result, with unit/confidence/reason/availability and sampled-Q metadata.
4. **Independent gate rounding/qualification loss — resolved here.** Before, `Build.tsx::useExportCheck` used `+g.value.value.toPrecision(4)` and omitted confidence/reason. It now exports the canonical finite gate value without independent rounding and includes unit, confidence, gate reason, and the value's qualification reason (`valueReason`). Non-finite gate values remain null.
5. **Duplicate KML terminal predicate — resolved here.** Preview and final make formerly repeated the nominal/termination conjunction. Both now call `hasKmlNominalTouchdown`, which combines the stricter explicit-touchdown requirement with shared `landingAvailability`; behavior is unchanged.
6. **No hidden duplicate physical formulas found.** Landing energy, drift, native maxima, rail-exit speed, and event values have no consumer-side physical recomputation. Recovery/Flight/Saved Runs/Build share the retained values and availability helpers. `RecoveryCard.tsx` is the packing/separation-charge card: it already delegates bay and charge equations to `src/recovery/packing.ts` and `src/recovery/charges.ts` and contains no flight-result or descent formula.

### Prior open findings, now resolved (dictionary revision `RMP10-C06/2`)

**F1 — native off-nominal flag:** resolved. `RunSummary.offNominalExcursion` is a required native-backed field; `toFlightRun` copies it, `Build.tsx::useExportCheck` exports `simulation.offNominalExcursion`, and new saved cases preserve it in `flightOutputs.flags` plus the flat `summary.offNominalExcursion`. Old records without it stay unknown.

**F2 — saved outputs were a subset with no qualification:** resolved for new records. `withRunCases` archives the canonical `flightOutputs` dictionary from `flightOutputDictionary` (including `maxQ`, `burnoutAltitude`, `weathercockAngleDeg`, units, confidence, reasons, availability, revision, flags and `sampledMaxQ`). ## 7. Qualification boundary

The dictionary establishes consistent names, sources, units, clocks, availability, precision, and consumers only. It does not establish continuous peak resolution, sensor agreement, guide geometry, per-section recovery energy, canopy inflation/opening-shock accuracy, measured weathercock behavior, structural loads, a validated operating envelope, or compliance with any competition rule. Those remain in the applicable RMP09/RMP10/RMP12–RMP17 scopes.
