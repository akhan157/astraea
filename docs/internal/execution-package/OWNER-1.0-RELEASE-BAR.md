## What the owner actually wants

- Astraea is a general-public rocket design/simulation product. Collegiate teams
  are its first focused customer group, not necessarily its only eventual users.
- The first intended customer is **Binghamton University's rocketry team**.
  The earlier Queen's reference was a transcription misunderstanding and is
  superseded. No official team-name spelling, team agreement, adoption, data
  permission or contact has independently been established.
- The owner's 1.0 requirement is a product the team can receive, use independently
  to design its rockets and obtain practical engineering value from. They are
  intended customers, not unpaid physics developers or a test laboratory expected
  to make an unfinished prototype trustworthy.
- "Whatever rocket they want" expresses support for meaningful design variation
  across the team's intended work, not only one preset, one fitted vehicle or
  the convenient cases the current diagnostic can run. It is not evidence that
  every conceivable staged/SRAD/active-control configuration is already required
  or supported. Actual team configurations/regimes remain to be established;
  never silently choose the current SB1 limits as the team's requirements.

## What must be true at a useful 1.0 handover

| User outcome | Release expectation, not a claim already met |
| --- | --- |
| Define and change designs | Usable geometry/component/motor/mass/CG workflows for the supported team design space; preserve actual features, units and provenance instead of silently simplifying the rocket |
| Make engineering comparisons | Compare meaningful motor, geometry, fin/CG and recovery alternatives with traceable inputs and explicit source/model identities; not one pre-tuned demonstration |
| Obtain useful predictions | Supported flight/event/stability/recovery outputs must be correctly defined, numerically checked and backed by appropriate evidence for the decisions the product offers; an unfinished bounded prefix is not a complete-flight result |
| Understand applicability | Per-output/model/domain uncertainty and limitations are clear. No hidden fallback, arbitrary confidence percentage or global validated badge. Warnings/refusals cannot substitute for supporting the core intended workflows |
| Keep and share work | Dependable save/open/import/export as applicable, reproducible saved results, versioned inputs/assumptions and another member able to use them without developer rescue |
| Install and operate | Tested, dependable interaction and applicable installed-platform/update/recovery behavior; mocked tests or backend examples alone do not establish a usable delivered app |

Normal engineering review and range/flight authorization still apply, as with
other engineering tools. This is not a promise that the simulator independently
authorizes flight or eliminates model uncertainty. Conversely, those caveats must
