# Alternative routes to collegiate primary-simulator accuracy

Research/access date: **2026-10-25**. Astraea source baseline: `761d6c3`; this packet supplements [model-path.md](model-path.md) and [data-path.md](data-path.md), without repeating their engine audit. No product edits, dependencies installed, engines run, flight outcomes inspected, external messages sent, purchases, pushes or deployments. Public method/software documentation and selected source files were inspected. Effort figures below are **engineering estimates**, not measured throughput or delivery commitments.

**Recommendation: keep the shared Rust/WASM trajectory authority, repair its force/moment contract, and support two explicit aerodynamic providers: a source-defined engineering model and configuration-specific supplied coefficient packets. Use RocketPy as the first independent trajectory comparator, OpenRocket as a separate geometry/aero comparator, targeted CFD only for a demonstrated coefficient gap, and empirical calibration as an auditable vehicle-specific supplement.** A wholesale engine swap removes some development burden but does not provide the missing independent collegiate measurements or make unknown drag/mass/weather known. This recommendation follows specific integration and export findings below, not a presumption that native development always wins.

## 2. B is implementable, but the source adapters are not interchangeable

### RASAero II: more than a drag exporter, less than a proven complete moment supplier

**Verified facts.** Official download documentation identifies **1.0.2.0**, Windows XP through 11, and .NET Framework **3.5**; software is free to download. Its [official download page](https://www.rasaero.com/dl_software_ii.htm) explicitly describes AeroPlots CSV export separately from flight-history CSV export. Free price is not an open-source redistribution license.

The [1.0.2.0 manual](https://www.rasaero.com/dloads/RASAero%20II%20Users%20Manual.pdf), printed pp64–77, documents maximum-body-area Sref in square inches and exporting AeroPlots via File → Export → To CSV File. Figure 94 was rendered and inspected: visible tabular headings include **Mach, Alpha, CD, CD Power-Off, CD Power-On, CA Power-Off, CA Power-On, CL, CN and CN Potential**. Thus a claim that RASAero only displays/exports drag is unsupported. However, **no actual CSV was generated here**, the horizontally hidden columns were not established, and independent **Cm export is not documented in the searched manual text**. Do not claim either a verified full six-component exporter or proof that Cm is absent from every runtime export. The UI permits selected Mach/angle plotting; precise batch coverage and file schema require the runtime check.

**Concrete acquisition spike:** on an already available Windows/.NET host, construct a synthetic canonical single-stage input with known nozzle/base, surface and reference settings; export zero-alpha powered/off and a signed incidence sweep at selected Mach/Re conditions. Record executable/input/export hashes, all headers and units, plotted versus exported values, source reference stations, Mach-Alt/reynolds conditions and output rights. No measured flight is needed. If no independent Cm exists, a source-defined CN-plus-CP moment can be reconstructed only under its stated static force/moment assumptions, with CP singularities handled; this cannot manufacture a free moment where CN is zero or supply damping. Qualify it as a limited provider, or pair it with directly measured/generated moments. Do not derive finite-alpha moment from zero-alpha CP without evidence.

**Rights/custody:** the manual carries Rogers copyright; no MIT/GPL code license or result-redistribution grant was established. Keep executable/manual outside product artifacts and do not copy algorithms from proprietary code. Distinguish user-produced coefficients, provider-distributed tables and copyrighted documentation; record the actual rights basis for each. A lack of explicit generated-data permission here is an **unresolved distribution condition**, not a finding that all numerical outputs are prohibited. Generation on a team machine can remain operationally useful before bundled-table distribution is resolved.

### OpenRocket: exact stable API is a workable generator, even when GUI documentation gets ahead of it

**Verified current stable choice.** GitHub's [latest release endpoint](https://api.github.com/repos/openrocket/openrocket/releases/latest) returned `release-24.12`, published 2025-07-27, on the access date. Its source tree SHA is `133b558de556f0282f51c3f53f3b3fc633b4310a`. Stable [build configuration](https://github.com/openrocket/openrocket/blob/release-24.12/build.gradle) targets Java 17. Stable [AerodynamicCalculator](https://github.com/openrocket/openrocket/blob/release-24.12/core/src/main/java/info/openrocket/core/aerodynamics/AerodynamicCalculator.java) exposes total and component calculations for supplied flight conditions, so a Java wrapper can sweep prescribed Mach/AoA/roll/Re inputs without running a flight. [FlightConditions](https://github.com/openrocket/openrocket/blob/release-24.12/core/src/main/java/info/openrocket/core/aerodynamics/FlightConditions.java) carries reference area/length, atmosphere and rates; incidence is a nonnegative total angle with separate lateral direction, requiring explicit conversion from signed paired Astraea angles.

Stable [AerodynamicForces](https://github.com/openrocket/openrocket/blob/release-24.12/core/src/main/java/info/openrocket/core/aerodynamics/AerodynamicForces.java) exposes CN, moment about coordinate origin, axial CA and airflow-parallel CD separately. But [BarrowmanCalculator](https://github.com/openrocket/openrocket/blob/release-24.12/core/src/main/java/info/openrocket/core/aerodynamics/BarrowmanCalculator.java) assembles each component's static Cm as `CN * CP.x / referenceLength`, before damping. That Cm API is valuable, not an independently measured static couple. Preserve the definitions rather than treating fields with identical names as identical physics.

The [current core integration guide](https://openrocket.readthedocs.io/en/latest/dev_guide/using_openrocket_core.html) documents standalone Java use and Maven dependency examples. The [live lookup-table guide](https://openrocket.readthedocs.io/en/latest/user_guide/advanced_flight_simulation.html) describes drag Mach/AoA tables and stability Cn/Cm/CP tables, edge clamping, embedded CSV and zero damping under table mode. **Do not infer those features are present in stable 24.12**: its recursively inspected tree has no lookup-named implementation. Use its verified calculation API for export; qualify any newer branch separately. Flight CSV contains along-trajectory samples, not a complete independent aero grid.

The [stable license](https://github.com/openrocket/openrocket/blob/release-24.12/LICENSE.TXT) is GPLv3-or-later with an additional permission for packaging non-compilable data. An external comparator is the lowest distribution commitment. If adopting code or shipping a core adapter, choose and document a GPL-compliant distribution; do not claim that a subprocess alone resolves every combined-work question. The [technical document and thesis have different Creative Commons terms](https://openrocket.info/documentation.html); method-reading and code-copying are different routes.

### CFD- or measurement-generated packet: stronger control over definitions, more work to earn trust

A recommended internal **design sketch**, not an existing importer, is:

```
manifest.json: schema/model IDs; geometry/source hashes; source rights;
              axes/signs; Sref[m2], Lref[m], moment datum[m];
              Re definition / environment / power / roll/cant;
              supported ranges; interpolation; uncertainty; exposure class
static.csv:   Mach,Re,alpha_rad,beta_rad,power,Cx,Cy,Cz,Cmx,Cmy,Cmz
rates.csv:    same state plus explicitly normalized rate derivatives
```

Choose one fixed body frame and moment datum; output total **force and moment**, then shift to instantaneous CG once. An analytic provider can generate the same packet for parity checks. No runtime executable or Python callable should be embedded in a portable data packet. Record absent rates as unsupported/assumed with uncertainty, not measured zeros. Power is a discrete state unless a justified continuous plume/nozzle model exists. A geometry-only cache key is insufficient if roughness, roll, Reynolds or source correction changes.

The first fixture should be synthetic, with a finite pure couple at zero transverse force, sign-reversed incidence and a moved CG; these discriminate against a CP-only implementation. Then ingest an already public NASA coefficient slice from `data-path.md`. Require positive-area/unit/datum validation, no duplicate conflicting states, declared grid completeness and explicit out-of-domain failure. Error from interpolation must fit the allocated coefficient/decision budget. Do not silently clamp an uncovered Mach/Re/AoA state merely because another engine does.

## 3. RocketPy is the strongest adoption candidate, but first prove the adapter

The [1.13.0 release](https://github.com/RocketPy-Team/RocketPy/releases/tag/v1.13.0), published 2026-07-22, and pinned [MIT license](https://github.com/RocketPy-Team/RocketPy/blob/v1.13.0/LICENSE) were verified. [Package metadata](https://github.com/RocketPy-Team/RocketPy/blob/v1.13.0/pyproject.toml) requires Python ≥3.10; [runtime requirements](https://github.com/RocketPy-Team/RocketPy/blob/v1.13.0/requirements.txt) include NumPy, SciPy, Matplotlib, netCDF4, requests, pytz, simplekml and dill. A Python service is operationally straightforward, but adds a hosted dependency; a desktop sidecar requires platform-specific locked packages, cancellation and native-library testing. A Rust translation is a substantive implementation/verification effort even with MIT source permission.

[GenericSurface documentation](https://docs.rocketpy.org/en/latest/user/rocket/generic_surface.html) supplies independent lift/side/drag and pitch/yaw/roll coefficients as functions of alpha, beta, Mach, Reynolds and rates, with explicit area/length scales. Alpha/beta are radians; CSVs use named independent-variable headers and a final coefficient column. Whole-vehicle moments need a consistent dry-mass datum and one application-point shift. Its z-forward frame and aerodynamic forces must be transformed into Astraea's y-forward convention. `cn` here is **yawing moment**, whereas RASAero `CN` is **normal force**. A filename or case-insensitive column matcher would corrupt that mapping.

**Source-level finding:** [pinned 1.13.0 GenericSurface](https://github.com/RocketPy-Team/RocketPy/blob/v1.13.0/rocketpy/rocket/aero_surface/generic_surface.py) accepts CSV, seven-argument callable/Function, or scalar zero. Although the guide describes constant scalar inputs, nonzero scalar values reach `TypeError` in `_process_input`; use an explicit callable or CSV. It also requests `natural` extrapolation in the table wrapper. Astraea should enforce its own qualified-domain guard rather than accepting that behavior as validated extension.

[Ordinary Rocket input](https://docs.rocketpy.org/en/latest/user/rocket/rocket_usage.html) takes powered/unpowered CD(M) curves; these need their own physical source. For a whole-vehicle generic force model, use one intentional source for each total force term and verify whether body drag is additionally applied; setting zero base drag may be required after source inspection. The spike must check zero incidence, pure moment, moved CG, signed pitch/yaw, atmosphere, mass depletion, rail first-rotation event and deployment timing against exact identities/common inputs. Adoption merits reconsideration if this demonstrates materially lower total qualification effort.

**Browser feasibility is conditional.** [Pyodide's current package list](https://pyodide.org/en/stable/usage/packages-in-pyodide.html) includes NumPy, SciPy, Matplotlib and netCDF4, so netCDF4 is not an established blocker. Actual RocketPy loading, optional imports, filesystem/requests adaptation, bundle/cache size, first-run offline behavior, worker cancellation and Monte Carlo parallelism have not been exercised. A bounded browser proof should self-host fixed runtime/wheels, disable network-dependent weather retrieval, use synthetic inputs, and measure startup/memory/trajectory latency in the existing app CSP. No browser port, speed or size claim is made here.

## 4. When CFD or empirical work wins

**CFD wins only after the disputed quantity is explicit.** A useful first question is whether one named transonic CN/moment slope or interference feature exceeds native-model uncertainty for a representative article. [SU2](https://su2code.github.io/) is LGPL 2.1 and offers compressible solvers; its [configuration template](https://github.com/su2code/SU2/blob/master/config_template.cfg) exposes Reynolds, incidence, turbulence/transition and normalization controls. Its [V&V collection](https://su2code.github.io/vandv/home/) demonstrates solver verification/validation activities, not validity for the chosen rocket.

A bounded proposal is one measured/reference geometry; three systematically refined meshes at a few preselected subsonic/transonic/supersonic sentinel conditions; farfield/symmetry and transition/turbulence sensitivity; signed small incidence for force/moment slopes; then additional Mach/AoA points only where the gap matters. Use 3-D geometry for actual fins; 2-D axisymmetry can diagnose body flow but cannot represent fin interference. Extrapolation across unsteady/shock/separation changes needs evidence. Cold-flow CFD and tunnel curves do not qualify powered base/plume effects. Validate against the public NASA coefficient sources before trusting configuration-specific predictions. No mesh, solver run or compute booking was performed.

**Greybox wins when repeat-flight inputs and observations identify a small correction.** Existing native coast fitting can support an explicitly vehicle-specific residual. Keep drag correction distinct from measured mass, thrust and atmosphere; inspect sensitivity/parameter correlation before fitting, score later flights or held-out vehicles, and retain fitted IDs. A calibrated CD curve used by both native and RocketPy solvers tests trajectories under common drag, not two independent aerodynamic models. Recovery CdA requires suspended-section mass and event-qualified descent, while rail speed and damping need their own observations. Black-box apogee-only fitting is a poor primary route because multiple wrong physical models can reach the same apex.

## 5. Decision sequence and fallback

1. **Commit to the common force/moment boundary and data contract first.** This is needed by A, B, C and D and resolves the existing interpretation defect. Keep prediction budgets/custody from the proposed accuracy specification; do not invent a pass threshold to select an engine.
2. **Compare two bounded spikes before a large rewrite:** native local-load correction plus one supplied-coefficient fixture; independently pinned RocketPy common-input adapter. Use a small OpenRocket coefficient extractor to inspect model differences. The three outputs should include explicit definition mismatches, domain failures and estimated production burden, not just apex agreement.
3. **Choose native+tables by default on present evidence.** It has the strongest compatibility with the shared browser/desktop/offline product and permits mission-specific transonic evidence without shipping a new runtime. Continue native engineering work for general design iteration; supplied-data runs disclose which providers support which decisions.
4. **Switch production trajectory to RocketPy only if the spike demonstrates a smaller end-to-end burden with the required runtime/output semantics.** Choose OpenRocket production integration if its domain/features and GPL distribution policy are acceptable and demonstrate a material benefit. Neither switch waives independent measurement.
5. **Commission CFD only for a residual coefficient question the public data/model comparison cannot close.** Fit empirical residuals only after event, force-definition and input defects are fixed. If qualified tables or independent flight packages are unavailable, maintain an explicit limited claim; no option justifies declaring primary collegiate accuracy from cross-code agreement alone.
